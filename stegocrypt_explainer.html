🔑 Password aur Key — Yahi Asal Raaz Hai

Password aur Key mein farq kya hai?

Password

Jo tum yaad rakhte ho: "MyDog123!"
Koi bhi length ho sakti hai
Human readable

Encryption Key

256 bits = 32 bytes = exactly fixed size
Random-looking numbers
AES ko exactly 256 bits chahiye

🗝️ Analogy: Password ek passphrase hai — "open sesame". Key ek actual physical key hai — exactly 256-bit metal ka tukra. Hum passphrase ko ek machine (scrypt) mein daalte hain jo exact key banaati hai.

Password directly key kyun nahi?

"hello" = sirf 5 bytes = 40 bits. AES ko 256 bits chahiye. Aur agar sab log "hello" use karein to attacker ek baar crack kare, sab ka data lega!

"hello" = h e l l o = 5 chars = 40 bits → NOT ENOUGH for AES-256 Solution: scrypt converts "hello" + random salt → 256 bits of strong key

Salt kya hota hai?

🧂 Analogy: Do log same password "hello" use karein. Salt ek random number add karna hai — jaise "hello" + [random 16 bytes]. Dono ka alag-alag key banega. Attacker ko har account alag crack karna hoga!

User A: scrypt("hello" + salt_A) → Key = [8E 3C F1 ... ] (32 bytes) User B: scrypt("hello" + salt_B) → Key = [A2 7D 9B ... ] (32 bytes) Same password, different salt → COMPLETELY DIFFERENT keys!

Salt random 16 bytes hoti hai — os.urandom(16) se generate hoti hai. Salt secret nahi hoti — ye payload ke saath store hoti hai. Lekin har encryption mein naya salt = har key alag.

Rainbow Table Attack kya hota hai?

🌈 Analogy: Socho attacker ne pehle se 1 million common passwords ki keys bana li hain aur ek table mein save kar li hain. Ab wo bas table check karta hai — ye Rainbow Table hai. Salt ki wajah se ye table useless ho jaati hai kyunki har salt ke saath alag key banti hai!

Password Strength — Simple Math

Password "ab": 2 chars, only lowercase → 26² = 676 possibilities → WEAK Password "Ab1!": 4 chars, mixed → 95⁴ ≈ 81 million → Better Password "StrongPass123!": 14 chars, mixed → 95¹⁴ ≈ 10²⁷ → STRONG Time to crack (with scrypt slowing things down): Weak: seconds Fair: hours Strong: billions of years → practically impossible

StegoCrypt requires minimum 8 characters. We recommend 12+.

NFKC Normalization — Unicode wali baat

Unicode mein ek hi letter alag-alag taraf likha ja sakta hai:

"é" — do tarike: 1. Single character: U+00E9 (NFC form) 2. Two characters: U+0065 + U+0301 (NFD form = "e" + accent) Dono same dikhte hain, lekin computer ke liye alag bytes! NFKC Normalization: dono ko same bytes mein convert karo NFKC("é" as U+00E9) → same output NFKC("é" as e+accent) → same output → Same key banega! ✅

⚗️ scrypt — Password Ko Key Mein Badalna

scrypt kya karta hai?

⚗️ Analogy: scrypt ek bahut mehenga, time-consuming factory hai. Tum apna password andar daalte ho, salt daalte ho — factory bahut saara kaam karti hai (RAM use karti hai, CPU use karti hai) aur output mein tumhe ek perfect 256-bit key milti hai. Ye deliberately slow hai — kyunki attacker bhi slow hoga!

scrypt ka formula:

Key = scrypt(Password, Salt, N, r, p, dkLen)
1
Password — tumhara original password (NFKC normalized, UTF-8 encoded)
2
Salt — random 16 bytes. Har baar naya. Rainbow tables se bachata hai.
3
N = 2¹⁴ = 16,384 — CPU/Memory cost. Iska matlab hai scrypt ko 16,384 baar ek operation karna hoga. Jitna bada N, utna zyada time aur RAM chahiye.
4
r = 8 — Block size parameter. RAM usage badhaata hai.
5
p = 1 — Parallelization. 1 matlab ek baar mein single thread.
6
dkLen = 32 — Output key length: 32 bytes = 256 bits = AES-256 ke liye perfect.

Memory Calculation:

RAM used by scrypt = 128 × N × r bytes = 128 × 16,384 × 8 = 16,777,216 bytes = 16 MB per attempt Attacker ke paas 10,000 computers hain aur sab brute-force karein: 10,000 × 16 MB = 160 GB RAM sirf ek second ke guesses ke liye → Practically impossible to brute-force! ✅

Ye slow kyun hai? Deliberately!

MD5 Hash (old, fast)

Password hash = 1 microsecond
Attacker: 1 billion guesses/second
8-char password: cracked in minutes!

scrypt (slow by design)

Password hash = ~100ms + 16MB RAM
Attacker: 10 guesses/second max
8-char password: billions of years!

scrypt Internal Steps (simple version):

1
PBKDF2 Setup: Password aur salt se initial blocks banao
2
ROMix: N baar memory mein random-access operations karo — ye RAM use karta hai, GPU/ASIC se speed nahi milti
3
BlockMix + Salsa20: Har block ko 64-byte chunks mein process karo
4
PBKDF2 Final: Output leke final key extract karo — exactly 32 bytes

Tumhe ye andar ka kaam yaad nahi rakhna — bas ye yaad raho: scrypt = password + salt → 256-bit key, aur ye bahut secure hai

🔒 AES-256-GCM — Encryption Algorithm

AES kya hai? (Advanced Encryption Standard)

🏭 Analogy: AES ek bahut complicated meat grinder jaisi machine hai. Tum plaintext daalo + key daalo → encrypted garbage nikalta hai. Same machine mein encrypted garbage + same key daalo → original plaintext wapas milta hai.

AES = US Government approved encryption standard (since 2001) Used by: banks, military, WhatsApp, Signal, HTTPS, everywhere AES-128: 128-bit key (2¹²⁸ possible keys) AES-192: 192-bit key AES-256: 256-bit key (2²⁵⁶ possible keys) ← We use this 2²⁵⁶ = 115,792,089,237,316,195,423,570,985,008,687,907,853, 269,984,665,640,564,039,457,584,007,913,129,639,936 (Universe mein atoms ki tadaad se zyada!) → Brute force karna = IMPOSSIBLE

AES kaise kaam karta hai? (Block Cipher)

AES ek baar mein 16 bytes (128 bits) process karta hai — ise "block" kehte hain.

1
SubBytes: Har byte ko ek lookup table se replace karo (S-box)
2
ShiftRows: 4×4 grid ki rows ko shift karo
3
MixColumns: Columns mein mathematical mixing (Galois Field multiplication)
4
AddRoundKey: Key ke saath XOR karo

Ye 4 steps 14 baar repeat hote hain (AES-256 mein 14 rounds). Itna zyada mixing ke baad koi pattern nahi bachta!

GCM kya hai? (Galois/Counter Mode)

GCM ek "mode" hai jisme AES use karte hain. Ye do kaam ek saath karta hai:

1. Confidentiality (Privacy)

Message encrypt hota hai — koi padh nahi sakta bina key ke

2. Authentication (Integrity)

Ek 16-byte "auth tag" banta hai — koi bhi bit change hone pe tag mismatch → automatic detection!

🔏 Analogy: GCM ek sealed envelope jaisa hai jo andar se lock bhi hai aur bahar tamper-proof seal bhi hai. Agar koi needle se andar likh de ya seal toda — envelope khulega hi nahi!

GCM mein Counter Mode (CTR) encryption:

Counter = Nonce (12 bytes) + Counter (4 bytes) Block 1: Encrypt(Key, Nonce || 0000001) → Keystream_1 Block 2: Encrypt(Key, Nonce || 0000002) → Keystream_2 ... Ciphertext_1 = Plaintext_1 XOR Keystream_1 Ciphertext_2 = Plaintext_2 XOR Keystream_2 XOR matlab: 1 XOR 1 = 0 1 XOR 0 = 1 0 XOR 1 = 1 0 XOR 0 = 0 (Ek baar XOR karo = encrypt, dobara same XOR karo = decrypt!)

Nonce kya hai?

🎲 Analogy: Nonce = "Number Used Once". Jaise har cheque par ek unique cheque number hota hai. Agar tum same cheque number dobara use karo — bank reject karta hai. Same tarah, same nonce dobara use = security completely breaks!

Nonce = os.urandom(12) → 12 random bytes = 96 bits Possible nonces = 2⁹⁶ = 79,228,162,514,264,337,593,543,950,336 Agar tum har second ek encryption karo: Time to repeat = 2⁹⁶ seconds ≈ age of universe × 2 billion → Practically impossible to repeat nonce! ✅

Auth Tag — Integrity Check:

GHASH function use karta hai: H = AES(Key, 0...0) [128 zero bits encrypt karo] Tag = GHASH(H, Ciphertext) XOR AES(Key, Nonce || 1) Tag size = 16 bytes = 128 bits VERIFY karte waqt: Recalculate tag from received ciphertext IF received_tag == calculated_tag → OK ✅ IF mismatch → TAMPERED! Throw error ❌ Wrong password → wrong key → wrong H → wrong tag → ERROR Corrupted data → tag mismatch → ERROR

Is liye wrong password pe hum "Incorrect password or corrupted data" show karte hain — AES-GCM automatically detect karta hai!

Output size calculation:

Ciphertext size = Plaintext size + 16 bytes (auth tag) Example: Message: "Hello World 🔐" = 15 bytes Ciphertext = 15 + 16 = 31 bytes Note: GCM stream mode hai — koi padding nahi lagti! (ECB/CBC modes mein padding lagti hai — GCM mein nahi)

📦 STGC Payload Format — Binary Structure

Payload kyun structure kiya?

📮 Analogy: Ek parcel bhejte waqt sirf item andar nahi daalt — ek address label bhi lagaate ho, weight likhte ho, sender info likhte ho. Receiver yahi dekh ke jaanta hai ke parcel kis ka hai, kya hai, kaha kholna hai. STGC payload bilkul aisa hi ek structured "parcel" hai!

Byte-by-byte structure:

BytesFieldSizeValuePurpose
0 – 3 Magic Header4 bytes S T G C Ye confirm karta hai ke ye StegoCrypt payload hai
4 Version1 byte 0x01 Future mein version 2 aaye to old images read ho sakein
5 – 20 Salt16 bytes Random bytes scrypt key derivation ke liye — secret nahi, payload mein store hai
21 – 32 Nonce12 bytes Random bytes AES-GCM decryption ke liye zaruri
33 – 36 Length4 bytes uint32 number Ciphertext kitne bytes ka hai — extractor ko exactly utna hi padhna hai
37 – end CiphertextN bytes Encrypted data Actual encrypted message + 16-byte auth tag
Total Header Size = 4 + 1 + 16 + 12 + 4 = 37 bytes (FIXED) Total Payload = 37 (header) + N (ciphertext) bytes

Length field — struct.pack kya hai?

Computer ko ek number (jaise 1000) exactly 4 bytes mein store karna hota hai. struct.pack('>I', 1000) ye kaam karta hai:

1000 in binary = 00000000 00000000 00000011 11101000 struct.pack('>I', 1000) → bytes: [0x00, 0x00, 0x03, 0xE8] '>' = Big-endian (bade byte pehle — network standard) 'I' = Unsigned Integer (4 bytes) struct.unpack('>I', b'\x00\x00\x03\xE8') → (1000,) # recover karein Maximum value = 2³² - 1 = 4,294,967,295 bytes ≈ 4 GB

Delimiter kyun nahi? (Like ###END###)

❌ Delimiter approach

Agar encrypted data mein naturally "###END###" bytes aajayein? → False end detected! Ciphertext binary data hai — koi bhi byte sequence possible hai

✅ Length-prefix approach

Pehle header se exact length parho → phir bilkul utne bytes parho → koi ambiguity nahi, koi false positive nahi

Magic Header ka fayda:

Extractor sab se pehle bytes[0:4] check karta hai: == b'STGC' → Yes! StegoCrypt payload hai ✅ != b'STGC' → "No StegoCrypt payload detected" error ❌ Is se: - Plain image upload karo → "not a stego image" error - Doosri app ki stego image upload karo → "not a stego image" - StegoCrypt image upload karo → proceed to decrypt ✅

Alpha channel kyun nahi use karte?

RGBA images mein 4th channel Alpha = transparency. Alpha 0 = fully transparent, Alpha 255 = fully opaque. Iska LSB change karo → pixel thoda transparent ho jaata hai → visually noticeable! Is liye hum sirf R, G, B use karte hain.

PNG vs JPEG — kyun PNG zaroori hai?

❌ JPEG (Lossy)

Ye image save karte waqt pixels CHANGE karta hai! R=215 → R=217 ya R=213 ho sakta hai. LSB data DESTROY ho jaata hai!

✅ PNG (Lossless)

PNG exactly same pixel values save karta hai. R=215 → R=215. LSB data preserved! ✅

📊 PSNR — Image Quality Measure

PSNR kya hai?

📻 Analogy: Radio signal mein "signal-to-noise ratio" hota hai — useful signal kitna zyada hai noise se. Image mein: original image = useful signal, stego changes = noise. PSNR zyada = noise kam = better quality.

PSNR original aur stego image ke درمیان difference naapti hai. Higher value = better (less distortion).

Step 1 — MSE (Mean Squared Error):

MSE = average of (original - stego)² for every pixel channel Har pixel ke liye: Original R = 214, Stego R = 215 Difference = 215 - 214 = 1 Squared = 1² = 1 Agar 1000 pixels mein 500 changed (by 1) and 500 unchanged: MSE = (500 × 1² + 500 × 0²) / 1000 = 500/1000 = 0.5

Step 2 — PSNR formula:

PSNR = 10 × log₁₀(MAX² / MSE) MAX = 255 (maximum pixel value for 8-bit image) log₁₀ = logarithm base 10 log₁₀(1) = 0 log₁₀(10) = 1 log₁₀(100) = 2 log₁₀(1000) = 3 log₁₀(10000) = 4 Example with MSE = 0.5: PSNR = 10 × log₁₀(255² / 0.5) = 10 × log₁₀(65025 / 0.5) = 10 × log₁₀(130050) = 10 × 5.114 = 51.14 dB ✅ (Excellent quality!)

LSB mein PSNR itna high kyun hota hai?

LSB change = maximum 1 per channel MSE calculation: If we change ALL pixels by 1: MSE = 1.0 (maximum possible for LSB) PSNR = 10 × log₁₀(255²/1.0) = 10 × log₁₀(65025) = 48.1 dB Realistic (only some pixels changed): MSE ≈ 0.05 to 0.3 PSNR ≈ 53 to 61 dB ← StegoCrypt typical range 61 dB matlab: difference itna chhota hai ke koi bhi nahi dekh sakta!

📈 SSIM — Structural Similarity

PSNR se SSIM kaise alag hai?

👁️ Analogy: PSNR ek lab instrument ki tarah hai jo sirf numbers measure karta hai. SSIM ek human eye ki tarah hai jo structure, texture, aur brightness ko holistically dekhta hai — jaise hum actually images judge karte hain.

SSIM teen cheezein compare karta hai:

L
Luminance (Roshan/Andhere): Average brightness same hai kya?
C
Contrast (Tezaab/Mulaayam): Pixel variation pattern same hai kya?
S
Structure (Shapes/Edges): Image ka structure (edges, textures) same hai kya?

SSIM Formula (simplified):

SSIM(x, y) = L(x,y) × C(x,y) × S(x,y) Where (in a small window/patch of pixels): μₓ = mean of patch x (average pixel value) μᵧ = mean of patch y σₓ = standard deviation of x (how spread out values are) σᵧ = standard deviation of y σₓᵧ = covariance of x,y (how they vary together) L(x,y) = (2μₓμᵧ + C₁) / (μₓ² + μᵧ² + C₁) C(x,y) = (2σₓσᵧ + C₂) / (σₓ² + σᵧ² + C₂) S(x,y) = (σₓᵧ + C₃) / (σₓσᵧ + C₃) C₁, C₂, C₃ = small constants to prevent division by zero

LSB mein SSIM itna high kyun?

LSB change = only 1 per channel Mean (μ) almost same raha → L ≈ 1.0 Standard deviation almost same → C ≈ 1.0 Covariance almost same → S ≈ 1.0 SSIM = L × C × S ≈ 1.0 × 1.0 × 1.0 ≈ 0.9999 StegoCrypt typical SSIM: 0.9998 to 0.9999

Window-based computation:

SSIM poori image ek baar mein nahi napti. Ye ek chota window (e.g. 7×7 pixels) slide karta hai poori image pe, har jagah SSIM calculate karta hai, phir average nikalta hai. Ye human vision system ko model karta hai — hum bhi locally dekhte hain!

🔄 Complete Flow — Ek Saath Sab Kuch

Ab jab sab concepts clear hain, ye dekho ke yeh sab milke kaise kaam karte hain "This is my secret message 🔐" example ke saath:

🔐 ENCRYPT & HIDE side:

1
Input:
Message: "This is my secret message 🔐"
UTF-8 encode: 30 bytes (emoji = 4 bytes)
Password: "StrongPassword123!" (18 chars)
2
Salt generate:
os.urandom(16) → [0xA3, 0x7F, 0xC2, 0x11, ...] (16 completely random bytes)
Ye salt payload mein save hoti hai — secret nahi
3
scrypt key derive:
scrypt("StrongPassword123!", salt, N=16384, r=8, p=1, len=32) → Key = [0x8E, 0x3C, 0xF1, 0x44, ...] (32 bytes = 256 bits) Takes ~100ms + 16MB RAM
4
Nonce generate:
os.urandom(12) → [0x4D, 0x9A, 0x01, ...] (12 random bytes)
5
AES-256-GCM encrypt:
AES_GCM.encrypt(key=32bytes, nonce=12bytes, plaintext=30bytes) → Ciphertext = 30 bytes + 16 bytes (auth tag) = 46 bytes (Completely random-looking encrypted data)
6
Build STGC payload:
b'STGC' = 4 bytes [magic] b'\x01' = 1 byte [version] salt = 16 bytes [random] nonce = 12 bytes [random] struct.pack('>I', 46) = 4 bytes [length] ciphertext = 46 bytes ───────────────────────────── Total = 83 bytes
7
Convert to bits:
83 bytes × 8 = 664 bits to embed
8
LSB embed in 400×400 image:
Capacity = 400 × 400 × 3 = 480,000 bits Payload = 664 bits Capacity used = 664/480,000 = 0.14% ← almost nothing! For each of 664 bits: channel_value = (channel_value AND 0xFE) OR payload_bit Maximum change per pixel: ±1
9
Save as PNG:
Exactly same pixel values preserved → LSB data safe ✅
PSNR ≈ 57 dB, SSIM ≈ 0.9999

🔓 EXTRACT & DECRYPT side:

1
Read first 37×8=296 LSBs → header:
bytes[0:4] == b'STGC' → ✅ StegoCrypt payload confirmed
bytes[4] == 0x01 → ✅ version 1
bytes[5:21] → salt (16 bytes extracted)
bytes[21:33] → nonce (12 bytes)
bytes[33:37] → length = 46
2
Read exactly 46×8=368 more LSBs → ciphertext
3
scrypt with password + extracted salt:
scrypt("StrongPassword123!", extracted_salt, ...) → same key as before ✅ (Salt stored in payload → receiver can derive same key!)
4
AES-256-GCM decrypt:
AES_GCM.decrypt(key, nonce, ciphertext) → Verifies auth tag (16 bytes) → PASS ✅ → Decrypts → 30 bytes plaintext → UTF-8 decode → "This is my secret message 🔐" ✅
❌
Wrong password "WrongPassword123" — kya hota hai?
scrypt("WrongPassword123", salt) → different key [0xC4, 0x12, ...] AES_GCM.decrypt(wrong_key, nonce, ciphertext) → auth tag mismatch detected → InvalidTag exception → User sees: "Incorrect password or corrupted hidden data." ✅ → No crash, no garbage output

✅ Security Summary

Even if attacker:

  • • Stego image haath lag jaaye → andar encrypted data hai, parhna impossible without password
  • • STGC format jaanta ho → 46 bytes ciphertext milega but decrypt nahi hoga
  • • 1 billion passwords/second try kare → scrypt ki wajah se actually 10/second max → billions of years
  • • Stego image mein koi bit change kare → AES auth tag fail → clean error
